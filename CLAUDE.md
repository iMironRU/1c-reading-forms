# Инструкции для Claude Code

Книга «Чтение форм 1С» — третья в линии «Чтение 1С» (код → дерево метаданных
→ форма → данные). **Написаны §0.1 и §0.2** (переписаны под канон v0.2.3),
остальное не начато. Следующий шаг — §0.3, там вводится центральная метафора книги.

Перед любым действием прочитай контекст:

- **`spec/constitution.md`** — метафора разговора, четыре несущих принципа,
  граница метафоры, запреты. Если предложение выходит за рамки конституции —
  откажись от него.
- **`spec/specification.md`** — для кого книга, метрики успеха, лестница
  упражнений, сквозные примеры, риски.
- **`spec/decisions.md`** — лог решений.
- **`docs/style-guide.md`** — канон серии плюс надстройка книги (в конце файла):
  платформа и стенд, слова плана и слова книги, мир «Канцтоваров», парная
  формулировка с адресом в редакторе, схемы трёх видов, упражнения, ответы.
- **`docs/00_plan_knigi.md`** — полный план всех 11 глав (версия 4).
- **`docs/plan.md`** — текущий статус и ближайший шаг.
- **`docs/konfiguraciya.md`** — что текст обещает от конфигурации. Пополнять
  при каждом новом объекте, форме, реквизите формы, команде, подсистеме,
  «Чужой форме».

## Платформа и стенд

- Эталон — **1С:Предприятие 8.3.27**. Работа в Конфигураторе, снимки экрана и
  сверка экранных деталей — на Windows-стенде автора, не на этой машине.
- Каждая непроверенная экранная деталь (пункт меню, вкладка, свойство, надпись,
  поведение) — со скрытой пометкой `<!-- FIXME стенд: … -->`; место для снимка —
  `<!-- СКРИН: … -->`. Видимых читателю оговорок «(проверить…)» не бывает.
- Список для стенда: `grep -rn "FIXME стенд\|СКРИН:" chapters`.

## Четыре несущих принципа (повторяются от первой главы до последней)

1. **Разговор.** Форма — реплика системы об одном объекте.
2. **Автогенерация.** Не задана форма явно — платформа строит её из метаданных.
3. **Клиент и сервер.** Данные на сервере, пользователь на клиенте; между ними
   ходят описание формы, её данные и обращения к серверу; окно формы строит и
   держит клиент. Клиент и сервер — роли, а не обязательно два компьютера.
4. **Декларативность.** Мы задаём правила, платформа сама строит и оживляет
   интерфейс. «Само сработало» = где-то в дереве задано правило.

## Главное правило письма

Каждая метафора немедленно получает **строгую пару с адресом в редакторе** —
вкладка, свойство, действие. Метафора без пары — дефект.

И строго разводим: **реквизит объекта** ≠ **реквизит формы**.

Для читателя разделы книги — **главы**, не модули: в 1С модуль — место для кода.
Номеров параграфов в тексте не пишем — направление, а не адрес.

## Команды

### `/book-write §N.N [тема]`
Порядок: конституция → спецификация → `docs/00_plan_knigi.md` (раздел главы) →
соседние параграфы → стиль с надстройкой → реестр конфигурации. `status: draft`.

### `/book-analyze §N.N`
Конституция → спецификация → стиль → консистентность. Отдельно проверяй:
у каждой метафоры есть строгая пара с адресом в редакторе? не смешаны ли
реквизит объекта и реквизит формы? есть ли задание в живом интерфейсе? у каждой
экранной детали есть пометка стенда? совпадает ли мир с реестром?

### `/book-plan модуль-N`
Уточнить состав главы по `docs/00_plan_knigi.md`; решения — в `spec/decisions.md`.

## Что не делать

- Не писать код обработчиков — ни строки. Обработчики в примерах пусты и помечены.
- Не разбирать `&НаКлиенте` / `&НаСервере` — только концепцию клиент-сервера.
- Не опираться на аналогии с вебом, мобильными или офисными интерфейсами.
- Не оставлять метафору без строгой пары.
- Не утверждать экранную деталь как проверенную без пометки стенда.
- Не менять в `metadata.yaml` версию и статусы напрямую — они ведутся через
  `./book.sh`; блок `modules:` правится руками.
- Не генерировать длинные тексты без запроса — сначала предложи план параграфа.
